# PathEditor 开发窗口

开发窗口是这条流水线的**执行端**：读计划、提异议、写代码、写回执、按审查意见整改。它与审核窗口不共享上下文，**唯一的交流媒介是仓库里的文档**——想说的任何事都必须落到文件里，否则对方看不到。

本 skill 的五条步骤对应五个阶段。每次进入先判明用户要推进哪一步，不要跳步。

---

## ⓪ 开工前

1. 读计划文档 `docs/superpowers/plans/YYYY-MM-DD-<feature>-implementation.md`，**同时读它引用的 spec**。计划是论证，spec 是权威；两者冲突时以 spec 为准，并把冲突记进回执。
2. 读 `## Global Constraints` 一节，逐条确认自己理解无误。
3. 确认本轮的用户授权：**是否允许提交？是否允许推送？是否允许升级版本号？是否授权真实注册表写入？** 每一项都要用户明说，上一轮的授权不延续。

---

## ① 读计划，提出不同的意见

**这一步不是走过场。** 计划是审核窗口在没看过实现细节的情况下写的，几乎必然有与现状不符的地方。你的职责是在动手前把它们挖出来。

逐任务检查：

- **路径与符号是否真实存在**？计划里写的文件路径、crate 名、函数名、参数顺序，逐个去仓库核对。历史事故：计划里的 `cargo test -p patheditor-cli --lib` 就是错的（bin-only crate，必须用 `--bins`）。
- **命令与参数是否真实存在**？例：`env get Path --user` 里的 `--user` 根本不存在，会被 clap 以退出码 2 拒绝。
- **任务之间是否自相矛盾**？A 任务产出的类型，B 任务用了吗？签名对得上吗？
- **任务自己是否自相矛盾**？它指定的测试与它指定的实现是否一致？它要求某个步骤结束时 clippy 转绿，但那个符号要到更后面的任务才被引用——此时不可能转绿。
- **是否要求了仓库规范认定为缺陷的东西**？（断言为空的测试、逐字复制的逻辑块、与既有契约冲突的写法）
- **是否漏了规格里的要求？** 拿 spec 的验收标准逐条对照计划任务。

做一张表：一行一个检查项，写「计划原文 / 实际情况 / 建议处理」。**带着这张表去和用户（及审核窗口）对话。**

异议要具体：给出证据（文件:行号、命令的真实输出），不要只说「感觉不对」。

---

## ② 打磨

异议提完后会有几轮往返。注意：

- **不要替审核窗口改计划文档**——那是它的产物。你的异议与理由通过对话提交，改由它落笔。
- 每一轮都要确认：**上一轮的异议被怎么处理了？** 是采纳、驳回、还是悬置？悬置的必须继续追问。
- 打磨收敛前**不要开工**。计划缺陷在编码阶段暴露的代价，比在纸面上暴露高一个数量级。

收敛的判据：你对「做什么、不做什么、怎么验证」与计划文本没有分歧，且计划里的错误已修正。

**核心细节必须落盘**（见 `patheditor-two-window-flow` 的「核心细节必须落盘为交接文档」）：异议、依据的代码位置或实验输出、最终裁断与理由，除了在对话里给用户看，还要在计划收敛后写入 `docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>核对轮交接.md`。用户是两个窗口之间的唯一信道，聊天输出会被截断或漏复制——**没落盘 = 对方不知道**。

## ③ 开发

### 3.1 用 superpowers 的执行技能

**调用 `superpowers:subagent-driven-development`**（推荐）或 `superpowers:executing-plans` 来逐任务执行。它们已经规定了：每个任务派全新实现者、任务后复审、账本记录、修复循环与上限。

### 3.2 隔离

在 worktree 中开发，不在 main 上直接改：worktree 位于 `.claude/worktrees/<name>`，分支名 `worktree-<name>`。worktree 内先 `npm install`。

若计划或 spec 在主目录尚未提交，worktree 从 HEAD 检出时看不到，**需要先 `cp` 进去**。

### 3.3 逐任务的质量门

每个任务结束都要跑，不允许攒到最后：

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p patheditor-cli --bins    # CLI 单测必须用 --bins
npm test
```

全部收口后再跑一次全量：`npm run verify`（必要时 `npm run verify:all`）。

### 3.4 纪律

- **遇到计划与实现冲突，先记录再决定**，把每一处偏离写进计划的 `## Execution Notes`（照 `docs/superpowers/plans/2026-09-17-cli-env-vars-implementation.md` 末尾那张「实际执行偏离记录」表的格式：计划原文 / 实际 / 处理）。
- **不写真实注册表**。所有单测必须是纯函数单测；E2E 用 mock IPC。真实注册表闭环测试**必须用户显式授权**，并记录备份路径、操作前后快照、回滚结果。
- **不实现规格外的功能**。合理但计划外的补全也要在回执里标出来，不要偷偷加。
- **不为了跑绿而改测试**。测试失败时先判断是实现错还是测试错；只有在测试确实写错时才改测试，并说明理由。
- 提交用 Conventional Commits。**不推送**，除非本轮已获授权。

### 3.5 完成的判据

不是「代码写完了」，而是：**计划里每个任务的验收标准都被验证过、质量门全绿、每一处偏离都有记录**。达不到就不要进入 ④。

---

## ④ 写开发回执（交接文档）

开发完成并经用户确认后，写回执交给审核窗口。

路径：`docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>开发回执.md`

照 `docs/审核和开发/2026.09.18/PathEditor-CLI环境变量开发回执.md` 的章节写：

```markdown
# <特性名> — 开发回执

**提交窗口**: 开发窗口
**日期**: YYYY-MM-DD
**交付对象**: 审核窗口
**分支**: ...
**版本**: ...
**状态**: 开发完成，质量门全绿，<未推送 / 已推送>

## 1. 交付内容概述

（做了什么 + 关键设计决策，每条写「选了什么 + 为什么」）

## 2. 代码改动清单

（按文件表格：改动量 + 说明）

## 3. 提交清单

（git log --oneline 逐条）

## 4. 测试与质量门

（新增测试表 + 质量门结果表，附实际命令输出）

## 5. 真实注册表闭环测试

（若未做，如实写「未做」；做了则写授权、前置、验证结果、零污染证明）

### 未覆盖项（如实列出）

## 6. 需要审核窗口重点关注的项

（已知保留项 / 本轮做的清理 / 已修正的事实错误 / 推送状态）

## 7. 交付物位置索引

（表格：交付物 → 路径）

## 8. 合并与分支状态
```

写法红线：

- **每一条结论都必须来自实际执行过的命令输出**，不许推测、不许把「应该没问题」写成「通过」。
- **未覆盖项必须如实列出**。这一节的价值最高——它让审核窗口知道哪些地方绿灯不代表安全。
- **已知保留项照实措辞**。例：Windows 注册表无 CAS，读-比-写仍有毫秒级竞态窗口，就写「缩小影响、不能完全消除 TOCTOU」，不许写成「原子操作」。
- 结尾签章，声明结论均基于实际输出。

回执写完，把路径告诉用户，交给审核窗口。

## ⑤ 接收审查报告并整改

审核窗口会交来**审查报告**（`PathEditor-<feature>审查报告.md`）。处理方式见 `superpowers:receiving-code-review`——**先核实，再动手，不做表演式同意**。

### 5.1 逐条核实

对报告里的每一条发现：

1. **读懂它的技术主张**，用自己的话复述一遍。
2. **去代码里核实**：它说的现象真的存在吗？它给的 `file:line` 对得上吗？
3. **判断是否适用于本仓库**：它会不会破坏既有功能？会不会违反 YAGNI（建议实现一个没人用的功能）？是否与用户此前的架构决策冲突？

### 5.2 分三类处理

| 结论         | 动作                                       |
| ------------ | ------------------------------------------ |
| **成立**     | 改，并说明改在哪一处                       |
| **不成立**   | 带技术理由写进回执反驳，不要沉默照做       |
| **无法核实** | 说明缺什么才能核实，向用户请示，不要猜着改 |

**报告里的建议如果与规格冲突，以 spec 为准**；确实是规格本身有问题，停下来找用户。

### 5.3 整改顺序

1. 阻塞性问题（破坏功能、安全问题）
2. 简单修复（拼写、导入）
3. 复杂修复（重构、逻辑）

**一项一改，每项单独验证，最后跑全量回归。** 不要一堆改动混在一起提交。

### 5.4 写复审回执

路径：`docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>复审回执.md`

照 `docs/审核和开发/2026.09.14/PathEditor-复审回执.md` 的章节写：

```markdown
# PathEditor <特性> 复审回执

## 1. 回执结论

（回执日期 / 复审对象 / 回执结论 / 版本状态 / Git 状态 / 注册表状态）

## 2. 日期与归档核对

## 3. 整改核对

### 3.1 已确认修复

（表格：复审项 / 核对结果 / 证据 file:line）

### 3.2 仍需保留的跨层项

## 4. 验证证据

### 4.1 已执行

（命令 + 实际结果）

### 4.2 未执行且不能声称完成

## 5. 残余风险

（R-01… 逐条，标 [非阻塞] / [阻塞]）

## 6. 回执判定
```

同样两条红线：**结论必须有命令输出支撑**；**未做的就写未做**。审核窗口会核对你的诚实度，含糊或夸大比承认未完成代价更高。

**本轮的核心细节须一并写入复审回执**（见 `patheditor-two-window-flow` 的「核心细节必须落盘为交接文档」）：哪条异议成立/不成立、依据的 `file:line` 或命令输出、改了哪一处、哪些仍待决。复审回执**同时是给用户复制给审核窗口的交接文档**——只写在聊天里等于没交接。

---

## 越界即停

需要删除文件、推送、升级版本号、写真实注册表；或计划/规格存在结构性缺陷、所有前路都是猜测——停下来问用户。
