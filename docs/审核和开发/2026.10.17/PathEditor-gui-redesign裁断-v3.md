## 二、V3 —— 审核窗口的错误（本节是裁断核心）

### 审核窗口 v2 说了什么

> 「`env-vars.spec.ts:71` 会假绿：`toHaveCount(0)` 在按钮移进未展开菜单后**永远为真**。必须改成先展开 ⋯ 菜单再断言。」

### 实际是什么

`env-vars.spec.ts:66-73` 的用例是：

```ts
test('「全部变量」下 PATH 专用按钮不可见', async ({ page }) => {
  await page.getByRole('button', { name: '全部变量' }).click(); // ← 切到 allVars
  await expect(page.locator('[data-env-var-key="user:JAVA_HOME"]')).toBeVisible();
  await expect(page.getByRole('button', { name: '上移' })).toHaveCount(0);
  await expect(page.getByRole('button', { name: '下移' })).toHaveCount(0);
  await expect(page.getByRole('button', { name: '一键清理' })).toHaveCount(0);
});
```

而 `AppShell.tsx:173-224`：

```tsx
{activeTab === 'allVars' ? <EnvVarToolbar ... /> : <ToolBar ... />}
```

**`allVars` 下 `ToolBar` 根本不渲染**，`EnvVarToolbar` 是独立组件。

### 所以

| 审核窗口的判断                | 事实                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------ |
| 「按钮进菜单后断言永远为真」  | ❌ 断言测的是「allVars 下不渲染 ToolBar」，**与按钮在 ToolBar 内部的位置无关** |
| 「必须改成先开 ⋯ 菜单再断言」 | ❌ **allVars 下没有 ⋯ 菜单**（那在 ToolBar 里），改了反而错                    |
| 「会假绿」                    | ❌ 不会。**它本来就该为真，且为真的理由是充分的**                              |

**审核窗口的错误根因**：**只读了断言本身，没读断言所处的渲染树**。「`toHaveCount(0)` + 元素可能被藏起来」在**同一个渲染树**里成立，但这里**根本是不同的渲染分支**。我把一个跨分支的计数断言，当成了同分支内的可见性断言。

### 真正的同类风险在哪

`tests/unit/app-shell-env-vars.test.tsx:193-203`：

```tsx
it('「全部变量」下 PATH 专用按钮不可见', async () => {
  render(<AppShell />);
  fireEvent.click(screen.getByText('全部变量'));       // ← 同样切到 allVars
  ...
  expect(screen.queryByRole('button', { name: '上移' })).toBeNull();
  expect(screen.queryByRole('button', { name: '下移' })).toBeNull();
  expect(screen.queryByRole('button', { name: '一键清理' })).toBeNull();
  expect(screen.queryByRole('button', { name: '导入' })).toBeNull();   // ← 注意
  expect(screen.queryByRole('button', { name: '导出' })).toBeNull();   // ← 注意
});
```

**这条同样是 allVars 分支**，`上移`/`下移`/`一键清理`/`导入`/`导出` **在 allVars 下都不该存在** —— 无论它们在 ToolBar 的哪个位置。**同样不会假绿。**

> **开发窗口把这条也列为「真正的同类风险」，审核窗口进一步确认：它也不是假绿风险。** 它的价值在于——**若有人把 `导入/导出` 从 ToolBar 移进 ⋯ 菜单，这条断言不会失败**（因为 allVars 下本来就没有 ToolBar）。**这是「测试覆盖不到变更」，不是「假绿」。** 二者有细微区别：假绿 = 断言永远为真；此例 = 断言在某个场景下有效，但不覆盖「按钮搬家」这个变更。

**更正后的准确表述**：

> **本波不存在「假绿」风险。** 存在的是「**跨分支断言无法检出按钮搬家**」——即 `allVars` 分支的 8 条 `toBeNull()` 断言（2 文件）不覆盖 ToolBar 内部布局变更。正确的应对不是改这些断言，而是**在主行场景下新增一条断言**：`crud-undo` / `import-export` 等已有的主行用例会覆盖「导入/导出可见」，这已经够了。

### 裁断

1. **撤回** v2 §H1 中「`env-vars.spec.ts:71` 会假绿，必须改」的结论。
2. **`env-vars.spec.ts:71` 归入「不受影响」**。
3. **`app-shell-env-vars.test.tsx:193-203` 归入「不受影响」**。
4. **H1 清单更正**：必须改的 E2E 从 5 个降为 **4 个**（`analyze` / `profiles` / `search-clean` / `toggle-save`）。

## 三、V1 —— 理由必须替换

### 开发窗口的指正

v2 的理由「放主行会让 800px 余量归零」**无法验证**：

- `width-test.html` 画的主行方案**本身就是「浏览已移出」的前提下画的**；
- 6 个 mockup 全文扫描，`浏览`/`Browse` 命中 **0 次**——**这个按钮从未被画过**。

> **审核窗口复核：完全属实。** 这是一个**「结论对、理由错」**的典型错误。理由错比结论错更隐蔽——结论错会被测试抓住，理由错只会被后来者当成真约束继承。

### 事实理由（替换后）

`handleBrowse` 的实质（`use-app-actions.ts`）：调用 Tauri `open({ directory: true })` 选目录 → `addPath`。即**「选一个目录并新增为一条路径」**，与「新建」是**同一件事的两种输入方式**。
→ 与新建语义重叠 + 低频（可直接粘贴路径）+ 主行已有 18 个按钮需收敛。

### 裁断

**维持 ⋯ 维护组首项**，理由替换为上述事实理由。

**备选方案（并入「新建」做下拉）不采纳**：按钮会从普通按钮变成复合控件，需要额外实现拆分按钮/下拉状态，成本高于收益。

## 四、V4 —— 改造清单漏 2 个文件

### 复核

`grep -rl -- "--app-list" src/components` 返回 **13 个文件**。其中：

- 7 个在 `dialogs/`（R7 范围外，用别名）
- 6 个在范围内：`PathTable` / `EnvVarTable` / `EnvVarToolbar` / `SearchInput` / `StatusBar` / `MergePreview`

v2 改造清单列了 **11 个文件**，但**缺 `MergePreview.tsx` 与 `EnvVarTable.tsx`**——二者只在「别名引用表」里被标为「范围内」。

### 后果

它们会**继续使用过渡别名**。而 Wave 4.1 的验收命令是 `grep -rn -- '--app-list' src/components/dialogs` —— **只查对话框**。这两个文件不在 `dialogs/` 下，**别名会被静默遗留**。

### 裁断

1. **改造清单补入** `path-list/MergePreview.tsx` 与 `env-list/EnvVarTable.tsx`。
2. **Wave 4.1 验收范围扩到整个 `src/`**：`grep -rn -- '--app-list' src` 结果为空（此时别名表本身也已删除）。

## 八、审核窗口自省

本轮审核窗口犯的错，性质上与它上一轮批评开发窗口的「D5 漏算 1 处」是**同一类**：**检查了断言的文字，没检查断言运行的上下文**。

- 上一轮：查了 `'确定'` 出现几次，没查**每处指向哪个元素**；
- 这一轮：查了 `toHaveCount(0)` 的形态，没查**它运行在哪个渲染分支**。

> **两次都是「局部正确、全局错误」。** 这说明「逐条核实」还不够——**必须核实到「这条断言在什么条件下执行、那个条件下 DOM 长什么样」**。此为审核窗口本轮的流程教训，记录在案。
