## 二、待裁断 A 的重新界定（本裁断的核心）

**报告与交接都把「长度预检」记成「TS ✅ / Rust ❌」，这是双方共同的措辞偏宽。** 追完整条调用链后，事实是：

```
save_path_with_sidecar            (core/src/service.rs:193)
 └─ write_hive_registry           (service.rs:83)
     └─ registry::save_system_paths  (registry/path.rs:95)
         └─ save_paths              (path.rs:48)
             └─ validate_and_join_paths  (path.rs:129)   ← 在此判 32767（path.rs:134）
```

**Rust 服务层并没有「缺」长度预检——它已在执行 Windows 的逐 hive 32767 上限**（`path.rs:134`，`value.encode_utf16().count() > 32767`）。真实差额只有一条：

| 约束                         | 是不是 **Windows 平台事实**？                                                    | 现状                           | 归属裁断                    |
| ---------------------------- | -------------------------------------------------------------------------------- | ------------------------------ | --------------------------- |
| 单 hive UTF-16 ≤ 32767       | **是**（注册表值上限）                                                           | core **已有**（`path.rs:134`） | **core 权威，本轮不动**     |
| `sys + user ≤ 32767`（组合） | **不是** —— 是 TS 自加的、比 Windows 更严的组合约束（`path-session.ts:114-117`） | 只在 TS                        | **属 GUI 软提醒，留在 GUI** |

**裁断**：

1. **逐 hive 上限**：core 是唯一真相源，**本轮零改动**。
2. **组合约束**：**不搬进 core**。它不是平台规则，是应用层的「有效 PATH 上限」软提醒（用户可 `force` 继续，`path-session.ts:118`）。搬它 = 引入 core 从未有过的新约束 = 行为变化，**与「收口 = 行为等价迁移」的目标相悖**。
3. **附带清理**：`src/config/default.json` 的 `maxSystemLength` / `maxUserLength`（`default.json:15-16`）与 core 常量重复，**删除**以免第二真相源；`maxCombinedLength`（`:17`）**保留**（GUI 组合软提醒用）。
4. **失败形态**：逐 hive 超限 → core 结构化 `HiveOutcome::Failed`（`service.rs:33`，**已如此**，非顶层 `Err`）；组合超限 → GUI 软提醒 + `force` 放行（**已如此**）。**两者是两回事，各回各家。**

> **对实施成本的影响**：开发窗口 A′ 的第 3 步「长度预检」**塌缩为空操作**（core 侧不做）。W-2 的实质步骤从「备份 + 并发 + 长度」变为「备份 + 并发」。
