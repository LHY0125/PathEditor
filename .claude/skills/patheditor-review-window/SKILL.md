# PathEditor 审核窗口

审核窗口是这条流水线的**上游**：确认要做什么、把做法讲清楚、最后判定做得对不对。它与开发窗口不共享上下文，**唯一的交流媒介是仓库里的文档**。

本 skill 的五条步骤对应五个阶段。每次进入先判明用户要推进哪一步，不要跳步。

---

## ① 与用户确认下一阶段任务与细节

在写任何文档之前，把「要做什么」问清楚。**一次只问一个问题**，等回答再问下一个——一次抛一堆问题会让用户漏答，而漏答的往往是安全边界。

事实类的信息（现有代码怎么写、某个文件在哪、上一次改了什么）**自己去仓库查**，不要问用户。只有**决策**才交给用户。

必问清单：

- 这一阶段的**目标**是什么？给出可判定的完成标准。
- **范围边界**：明确不做什么。PathEditor 的历史教训是范围蔓延（scope creep）比缺失更难审。
- **安全边界**：是否触及注册表写入、权限判定、敏感值、并发契约？
- **这一轮是否授权提交 / 推送 / 升级版本号？** 上一轮的授权不延续，每次都重新确认。
- 是否有**已知的取舍**需要先拍板？

用户回答后，先口头复述一遍你的理解（三五行即可），让用户确认无误再进入 ②。

---

## ② 编写开发文档

写两份，顺序不能颠倒。

### 2.1 设计文档

路径：`docs/superpowers/specs/YYYY-MM-DD-<feature>-design.md`

参照 `docs/superpowers/specs/2026-09-17-cli-env-vars-design.md`。必须包含：

| 小节            | 内容                                                             |
| --------------- | ---------------------------------------------------------------- |
| 背景与目标      | 为什么做，做完判定标准是什么                                     |
| 命令 / 接口规格 | 逐条列出新增或变更的对外接口，参数、默认值、退出码、错误语义写全 |
| 关键设计决策    | **每条决策写清「选了什么 + 为什么 + 放弃了什么」**               |
| 安全边界        | 哪些判定由 core 负责、哪些绝不能在前端/CLI 重复实现              |
| 验收标准        | 可逐条勾选的清单                                                 |
| 不在本版范围    | 明确排除项                                                       |

### 2.2 实施计划

路径：`docs/superpowers/plans/YYYY-MM-DD-<feature>-implementation.md`

**先调用 `superpowers:writing-plans` skill 拿到计划格式规范**，它规定的头部与任务结构是硬要求。然后照 `docs/superpowers/plans/2026-09-17-cli-env-vars-implementation.md` 的实际样式写。

必须有的头部：

```markdown
# <特性名> Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 一句话
**Architecture:** 两三句
**Tech Stack:** 关键依赖
**Spec:** `docs/superpowers/specs/...-design.md`

## Global Constraints
```

`## Global Constraints` 里**逐条抄写本轮适用的仓库硬约束**（分支、架构边界、文档注释要求、代码风格、质量门命令、禁止真实注册表写入、提交规范、退出码契约……），每条一行、值写死。每个任务都隐含继承这一节。

然后是任务：`### Task N: <名称>`，带 `**Files:**`（Create/Modify/Test，写精确路径）、`**Interfaces:**`（Consumes / Produces，写精确签名），以及带复选框的步骤：写失败测试 → 跑测试确认失败 → 写最小实现 → 跑测试确认通过 → 提交。

**禁止占位符**：不写「TBD」「TODO」「适当处理错误」「参考 Task N」。每个代码步骤要有完整代码块，每个测试步骤要有完整测试函数体。

结尾补两节：`## Self-Review`（规格覆盖 / 占位符扫描 / 类型一致性）与 `## Execution Notes`（留给开发窗口回填偏离记录）。

### 2.3 写完自查

对照 spec 逐条问：**这条要求落在哪个 Task 上？** 指不出 Task 的补上去。再检查计划里后出现的函数名、参数顺序是否与先定义的一致。

## ③ 与开发窗口打磨

开发窗口会**对计划提出异议**（可能多轮）。这一阶段你的职责是**裁断**，不是复述自己。

- 异议成立 → 改计划，并在文档里留下改动痕迹（改哪条、为什么改）。
- 异议不成立 → 说明理由，把理由写进文档，别只在对话里说。
- 异议指向**规格层面**（要求本身有问题）→ 停下来找用户，规格归用户拍板。

**每一轮打磨的产物都必须是文档更新**，不是口头共识。开发窗口看不到你的会话。

裁断结果写进计划文档（改哪条、为什么改），**并把该轮核心细节落盘**为 `docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>核对轮交接.md`（见 `patheditor-two-window-flow` 的「核心细节必须落盘为交接文档」）：开发窗口提了哪些异议、你的裁断与依据、哪些改了计划、哪些悬置待决。用户是两窗口之间的唯一信道，聊天输出会被截断或漏复制——**没落盘 = 开发窗口不知道**。

打磨收敛的判据：**双方对「做什么、不做什么、怎么验证」没有分歧**。达到这个状态才放行开发。

## ④ 审核开发窗口的代码

开发窗口在开发完成后会交来**开发回执**（`docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>开发回执.md`）。收到后按下面的顺序审。

### 4.0 先做三件事

1. 读开发回执全文，**尤其读 `需要审核窗口重点关注的项` 与 `未覆盖项`**——开发窗口主动标出来的地方通常是真问题。
2. 核对该回执声明的提交、文件、行数**是否与 git 实际一致**（`git log --oneline`、`git diff --stat`）。
3. **自己跑一遍质量门**，不采信回执里的数字。至少：`cargo fmt --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`、`npm test`。

> **回执不完整时不要凭记忆补**：核对轮交接（`PathEditor-<feature>核对轮交接.md`）、开发回执、审查报告、复审回执构成完整交接链。若某轮缺少对应文档，**先去仓库里找**（`docs/审核和开发/YYYY.MM.DD/`、计划的 `## Execution Notes`、`.superpowers/sdd/` 账本）；确实没有就向用户指出该轮未落盘，不要靠对话残片推断。

### 4.1 验证证据

逐项执行并记录命令与原始结果。**绿灯不等于规格全覆盖**——这句话要写进报告。

### 4.2 Standards 轴（规范符合性）

对照 `CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` 逐条查。必查项：

- `gui` / `cli` 是否**只做参数转换、命令分派、错误呈现**，业务规则是否都在 core
- **CLI 侧零安全判定逻辑**：保留名、保护名单、`Unsupported` 类型、hive 写权限、revision 校验必须全部由 core 判定
- 所有 `pub fn` / `pub(crate)` 是否有 `///` 文档注释
- 组件与 Store 是否**只经 `src/services/backend.ts`** 调 IPC，没有直调 `invoke`
- `src/core/` 是否零 React / Tauri 依赖
- 错误判定是否只认 `[E_CONFLICT]` **前缀**，没有靠中文文案做控制流
- `AGENTS.md` 与 `CLAUDE.md` 是否字节级一致
- Conventional Commits 是否合规
- 是否有**死导出**、行文与实现不符的注释（例如把「读后写」写成「原子操作」）

分三档写：`### 硬性违反`、`### 判断性意见`、`### 合规亮点`。

### 4.3 Spec 轴（规格符合性）

分三类写，**每类都要有**：

- `(a) 规格要求但缺失或只做一半` —— 逐条对照 spec 验收标准
- `(b) 规格没要求但做了的行为（scope creep）` —— 合理补全也要列，注明「合理但未在规格内」
- `(c) 实现与规格/计划不符` —— 逐条指出偏差点与计划对应位置

**测试缺口要单独较真**：公开 API 是否有直接调用测试？P0 安全场景（如 Path 过滤、保护名单拒写）是否只在 mock/前端单测里被间接覆盖？`npm run verify` 全绿**不能**证明这些被覆盖。

### 4.4 用子代理复核（可选但推荐）

改动超过 30 行或涉及安全边界时，可派 `code-reviewer` / `security-reviewer` 子代理独立跑一遍，再与自己的结论合并。**不要**把自己的判断预先塞给对方。

## ⑤ 写审查报告

路径：`docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>审查报告.md`

照 `docs/审核和开发/2026.09.17/PathEditor-全环境变量分支审查报告.md` 的章节写：

```markdown
# PathEditor <特性> 审查报告

- **审查日期**：
- **被审分支 / 提交**：
- **基准点**：
- **范围**：（N 个提交，M 个文件，+X / −Y 行）
- **功能**：
- **规格来源**：spec 与 plan 的路径
- **规范来源**：`AGENTS.md` / `CLAUDE.md`、`CONTRIBUTING.md`
- **复现命令**：`git diff main...<branch>`

## 提交清单

（git log --oneline 逐条）

## 一、验证证据

（命令 → 结果表，附「绿灯 ≠ 规格场景全覆盖」）

## 二、Standards 轴

### 硬性违反

### 判断性意见

### 合规亮点

## 三、Spec 轴

### (a) 规格要求但缺失或只做一半

### (b) 规格没要求但做了的行为（scope creep）

### (c) 实现与规格/计划不符

## 四、总结

### 合并前建议整改（按优先级）
```

写法要求：

- **文件:行号**定位每个发现，不要泛泛而谈。
- 说明**为什么重要**，不是只描述现象。
- **如实列出合规亮点**——准确的肯定让开发窗口更愿意接受其余意见。
- 建议整改**按优先级排序**，区分「必须改」与「可延后」。
- 未覆盖项、已知保留项照实写，不替开发窗口兜底。

写完后把报告路径告诉用户，并说明本轮的判定：**可以进入下一阶段 / 需要整改后复审 / 阻塞**。

## 复审回执的处理

开发窗口整改后会交来**复审回执**（`PathEditor-<feature>复审回执.md`）。按 `docs/审核和开发/2026.09.14/PathEditor-复审回执.md` 的对应结构核对：

- 逐条核对回执声明的整改项**是否真的落到代码里**（`file:line` 证据）。
- 核对回执里的「未执行且不能声称完成」是否诚实——如果它声称完成了但证据不足，指出来。
- 残余风险是否被如实列出。
- 判定本轮是否通过；不通过就再写一份审查报告，说明剩余问题。

## 越界即停

需要删除文件、推送、升级版本号、写真实注册表；或发现规格本身有结构性缺陷——停下来问用户。
