# PathEditor 双窗口协作总纲

PathEditor 的开发由一个**审核窗口**和一个**开发窗口**交替推进。两者是**独立会话**——它们之间不共享上下文，**所有交流都通过仓库里的文档完成**。这条约束决定了下面的一切：凡是希望对方知道的事情，必须落到文件里。

本 skill 是路由。判明当前会话的角色后，**立即调用对应的窗口 skill**，不要凭本文件直接开工。

## 判定当前角色

| 用户说什么       | 当前窗口         | 调用的 skill               |
| ---------------- | ---------------- | -------------------------- |
| 「你是审核窗口」 | 审核窗口         | `patheditor-review-window` |
| 「你是开发窗口」 | 开发窗口         | `patheditor-dev-window`    |
| 含糊 / 未声明    | **先问，不要猜** | ——                         |

角色由用户宣告，不由任务内容推断。用户说「审核这次开发」可能是在审核窗口派开发窗口的活，也可能是在开发窗口自查——问清楚再走。

## 一条特性的完整生命周期

```text
审核窗口                                    开发窗口
────────                                    ────────
①与用户确认需求与细节
        │
        ▼
②写 spec + 计划 ──────── 计划文档 ────────▶ ③a 读计划、提异议
        ▲                                              │
        │                                              ▼
        └────────── 异议与打磨（可多轮）◀─────── ③b 打磨
                                                       │
                                                       ▼
                                              ③c 开发（质量门全绿）
                                                       │
        ◀────────── 开发回执 ─────────────────────────┘
        │
        ▼
④审核代码与架构
        │
        ▼
⑤审查报告 ─────────────────────────────▶ 接收、整改
        ▲                                              │
        │                                              ▼
        └────────── 复审回执 ◀──────────────── 写回执 / 或退回
```

一个来回**只走一轮**：审查报告里的问题在开发窗口整改后由回执回复，审核窗口下一轮再决定是否复验。不要在单轮里反复拉锯——每一轮都必须落一个文件。

## 交付物必须固定到这些路径

两个窗口都**只认这些路径**，不要另起名字或换目录：

| 交付物               | 路径                                                             | 作者     |
| -------------------- | ---------------------------------------------------------------- | -------- |
| 设计文档 (spec)      | `docs/superpowers/specs/YYYY-MM-DD-<feature>-design.md`          | 审核窗口 |
| 实施计划             | `docs/superpowers/plans/YYYY-MM-DD-<feature>-implementation.md`  | 审核窗口 |
| 开发回执             | `docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>开发回执.md`     | 开发窗口 |
| 审查报告             | `docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>审查报告.md`     | 审核窗口 |
| 复审回执             | `docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>复审回执.md`     | 开发窗口 |
| 闭环测试记录（可选） | `docs/审核和开发/YYYY.MM.DD/PathEditor-<feature>闭环测试记录.md` | 开发窗口 |

日期用当前系统日期（Asia/Shanghai）。目录日期与文档内日期必须一致。

这些目录里已有先例，**动手写之前先读同目录下最近的一份**，照它的章节结构写——比任何模板都准。历史位置见 `docs/审核和开发/2026.09.17/` 与 `docs/审核和开发/2026.09.18/`。

## 两个窗口都要守的硬约束

来自仓库 `CLAUDE.md` / `AGENTS.md`，任何一轮都不得违反：

- **不删除任何文件**，未经用户书面同意。
- **不提交、不推送、不升级版本号**，未经用户明确要求。提交是否获授权按轮次重新确认，上一轮的授权不延续。
- **不写真实注册表**，除非用户显式授权；授权后必须记录备份、操作前后快照与回滚结果。
- **E2E 用 mock IPC**，永远不碰真实注册表。
- **`PathEditor` CLI 单测必须用 `cargo test -p patheditor-cli --bins`**（bin-only crate，`--lib` 会报 `no library targets found`）。
- 聊天用中文，代码注释用中文。

## 交付纪律

- 两份文档（`AGENTS.md` 与 `CLAUDE.md`）必须**字节级一致**——改一份就同步另一份。
- 任何「绿灯」「通过」「已修复」的结论，必须附**实际执行过的命令与输出**。没跑过的不要写。
- 未覆盖项、已知保留项、残余风险**如实列出**，不粉饰。历史文档里 `### 未覆盖项（如实列出）`、`[非阻断]` 这类小节是刻意的，保留这个习惯。

## 越界即停

出现下面任一情况，停下来问用户，不要自作主张：

- 需要删除文件、推送、升级版本、写真实注册表
- 特性范围发生变化，或发现计划本身有结构性缺陷
- 两个窗口对同一条需求的理解冲突，文档里没有权威答案
